総評

v2のSecurity Boundary（Value / Destination の2本立て）、askSecret() が値を返さない型、stdin承認の廃止、Vercel development除外、fail closed方針は、いずれもコードとSECURITY.mdの実態と整合していて正しい方向です。設計の作り直しは不要です。

ただし v2 は、脅威の入力面を「repository設定 / git remote / Agentの説明文」に限定しています。実コードを読むと、Destination を実際に決めているのは repository ファイルではなく「子プロセスの cwd と環境変数」 であり、この2つはどちらもAgentが定義上完全に支配します。ここがv2の最大の穴で、Blockerはすべてこの一点に集約されます。

Confirmed

C1. deploy子プロセスがenvを丸ごと継承する → repositoryを一切触らずにdestinationを乗っ取れる

severity: High / affected: §3.2, AC-7, §15-5

根拠

コードベース全体で、spawn / spawnSync に env: オプションを渡している箇所が1つもありません。

- packages/core/deploy/which.ts:59-64 — spawn(resolved.absolutePath, args, { ...options, shell: false })。呼び出し元 handoff.ts:84 が渡す options は { windowsHide: true } のみ。
- packages/adapters/shared.ts:20-32 — runCliSync も同様（wrangler whoami / vercel whoami / gh auth status が全部これ）。

つまり wrangler / vercel / gh は process.env をそのまま受け取ります。3社ともdestinationを環境変数から決められます（GH_TOKEN、CLOUDFLARE_API_TOKEN / CLOUDFLARE_ACCOUNT_ID、VERCEL_TOKEN / VERCEL_ORG_ID / VERCEL_PROJECT_ID）。

exploit

GH_TOKEN=<攻撃者のtoken> npx api-key-case deploy PROD_KEY --target github --env production

Agentは通常のshell tool callを1回撃つだけです。ファイル書き込みもbinary差し替えも不要。しかも gh auth status（github.ts:23）も同じ GH_TOKEN を見るので、identity probeと実行先が一貫して攻撃者側になり、v2 §3.2の「API Key Case自身が現在状態から解決する」を通過します。

なぜ「悪意ある任意コード」の除外範囲に入らないか

env変数をspawn時に1つ足すのは、Threat Modelが除外した keyring API直叩き / debugger / process injection のどれでもありません。Agentが正規インターフェース（npx api-key-case deploy）を正規の方法で呼ぶだけです。AC-7 は「repository config / git remote等を書き換えるだけで」と書いていますが、env はそれより弱い操作で同じ結果を出します。

最小修正案

v2 §3.2のDestination Identity構成要素に provider認証環境変数 を明記し、次の2つを要求する。

1. identity probe と実行を 同一のenv snapshot で行う（checkCli() 時点の process.env を凍結して runWithSecret へ渡す）。
2. provider認証env（上記6変数）を destination fingerprint に含める。承認時と実行時で異なれば中止。あるいはより単純に、actor: agent の自動deployでは provider認証envが存在する時点で fail closed（人間の環境には通常無いため実害が小さい）。

§15-5 を「destination設定変更」→「destination設定変更（repositoryファイル および環境変数）」へ書き換える。

C2. deploy子プロセスの cwd が projectDir ではなく process.cwd() → 承認した宛先と実行される宛先が別物になる

severity: High / affected: §3.2, AC-7, §15-5, §15-6

根拠

- packages/core/deploy/handoff.ts:84 — spawnResolvedCli(resolved, args, { windowsHide: true })。cwd を渡していない → 子は process.cwd() を継承。
- packages/adapters/shared.ts:20-32 — runCliSync も cwd 無し。
- 一方 packages/core/deploy/engine.ts:38 は adapter.detect(request.projectDir)、engine.ts:56 の hasSecret も projectDir 由来の projectId（cli/index.ts:652, vault/naming.ts:7）。
- packages/cli/index.ts:746 — const targetDir = positionals.length > 1 ? resolve(positionals[1]) : process.cwd(); つまり projectDir は argv で任意に指定できる。
- packages/mcp/tools.ts:177 — MCPの path 引数でも同じ分離が起きる。

3社ともdestinationはcwdから決まります（wrangler.tomlの name/env、.vercel/project.json の projectId/orgId、gh のgit remote）。

exploit

cd /tmp/attacker-repo                                   # remote = 攻撃者のGitHub repo
npx api-key-case deploy PROD_KEY --target github --env production /home/user/real-project

- deriveProjectId("/home/user/real-project") → 本物のprojectスコープSecretを読む
- adapter.detect("/home/user/real-project") → git.ts:68 は cwd: rootDir を渡すので、detect結果は本物のremoteを報告する
- Deploy plan / 承認ダイアログには「github.com/user/real-project / production」と表示される
- runStep の spawn は cwd = /tmp/attacker-repo → gh secret set は攻撃者のrepoへ書く

人間は正しい宛先を見てYesを押し、Secretは別のrepoへ行きます。v2 §3.2の「承認対象となったresolved planと実行対象を同一snapshotとして扱う」は、identityの解決元（projectDir）と実行の決定元（cwd）が構造的に別物なので、そもそも同一snapshotになり得ません。

より単純な変種として、positional無しで cd /tmp/attacker && npx api-key-case deploy KEY --target github --scope user も成立します（user scopeなのでprojectId不一致を回避）。

最小修正案

v2に1文追加する — 「Destination Identityの解決、plan表示、承認、実行は、単一の明示的なworking directoryで行う。process cwdが暗黙にdestinationを決めてはならない。」

実装側の最小差分は handoff.ts / shared.ts の spawn に cwd: projectDir を渡すこと（2行）。加えて、実行cwdと projectId 導出元の realpathSync 結果が一致しない場合は中止する検査を engine に置く。§15-6 のTOCTOU項目に「approval時のcwdと実行時のcwdの同一性」を明記。

C3. Human Plane helper自身が PATH / env 経由で差し替え可能

severity: Critical（§7の前提が崩れる） / affected: §7.1, §7.2, AC-3, §15-2

根拠

コード上、外部プロセスの解決は例外なくPATH依存です。

- packages/core/deploy/which.ts:17 — const pathValue = pathOverride ?? process.env.PATH ?? process.env.Path ?? ""（pathOverride はテスト専用、which.ts:14 のコメント通り）
- packages/core/git.ts:68, packages/core/gitignore.ts:36 — spawnSync("git", ...) はbare名でOS任せのPATH解決
- env のサニタイズは前述の通りゼロ

SECURITY.md:27 は「PATHのみから解決するので、悪意あるrepositoryが偽CLIを差し込めない」と書いていますが、これは node_modules/.bin に対する防御であって、プロセスのPATHを設定する親（= Agent）に対する防御ではありません。

v2 §7.2 は macOS/Windows について「安全性を確認できるOS-native / detached human interaction surface」としか書いておらず、helperをどう解決するかを規定していません。素直に spawn("osascript", ...) / spawn("powershell", ...) と書けば、Agentが用意した偽helperが起動し、人間がそこにSecret本文を打ち込みます。 Node製helperを process.execPath で起動する場合も、NODE_OPTIONS=--require ./evil.js が効きます。

これは「値をLLM context / transcriptへ流さない」というThreat Modelの第一項目に直撃する経路で、しかもファイル1個の書き込みとenv 1個の設定だけで成立します。debugger も injection も不要です。

最小修正案

v2 §7.2 に、backendの実装条件として次を追加する。

- Human Plane helperの実行ファイルは OS固定の絶対パスから解決する（/usr/bin/osascript、%SystemRoot%\System32\WindowsPowerShell\v1.0\powershell.exe 等）。PATH解決を使わない。
- helperプロセスは サニタイズしたenvで起動する。最低限 PATH / NODE_OPTIONS / DYLD_* / LD_PRELOAD / DISPLAY を継承しない。
- 上記を満たせないOS/条件では handoff-only へ fail closed する（Linuxの扱いを他OSにも一般化する）。

§15 に新規テストを追加：「PATH先頭に偽helperを置いた状態でHuman Planeを起動しても、偽helperが実行されない」。

（Linuxを handoff-only にする §7.2 の判断自体は正しく、C3はそれを Windows/macOS へ広げる話です。設計変更ではありません。）

C4. 承認↔実行の間でCLIバイナリが二重解決される（TOCTOU）

severity: Medium / affected: §3.2, §15-6

根拠

resolveCli が1回のdeployで2回、別々のタイミングで走ります。

- 1回目: engine.ts:45 adapter.checkCli() → shared.ts:15 resolveCli(command)
- 2回目: handoff.ts:58 → runStep → which.ts:73 resolveCli(cliName, pathOverride)

この2回の間に engine.ts:56 の keyring アクセス、engine.ts:66-76 のplan表示、そして engine.ts:86 の confirmProduction が挟まります。

v2はこの窓を意図的に広げます。 現状は「人間が yes と打つ数秒」ですが、v2 §8のHuman Planeダイアログでは人間の判断時間（分単位もあり得る）になります。その間に解決済みパスのファイルを差し替えれば、identity表示に使ったバイナリと値を渡すバイナリが別物になります。

最小修正案

v2 §3.2の「同一snapshot」を具体化する：承認planは ResolvedCli（絶対パス＋size＋mtime＋可能ならinode/file id）を保持し、spawn直前に再stat して一致しなければ中止する。 「可能なら」ではなく必須要件にする。C1のenv snapshot、C2のcwdと合わせて、これが「同一snapshot」の実体的な定義になります。

C5. deploy --force は provider側の既存値を削除する。§11はvault削除しか論じていない

severity: Medium / affected: §10, §11, AC-8

根拠

packages/adapters/vercel.ts:45-55 — --force 指定時、本体の前に vercel env rm <NAME> <env> --yes を preSteps として実行します。engine.ts:84 の確認分岐は env === "production" || adapter.id === "github" だけなので、vercel --env preview --force は人間確認なしで既存Secretを削除して置き換えます。

packages/adapters/cloudflare.ts:48 の overwriteWarning: true（wranglerは常に上書き）も同様に無確認です。

v2 §11はSecret lifecycleを「vault内の削除」としてのみ扱い、破壊的操作としてHuman Planeを通す設計にしていますが、provider側の破壊的操作（--force）は §10 のdeploy policyにも §11 にも出てきません。 v2 §10で「Vercel previewは自動化候補」とした瞬間、--force 付き自動deployが既存値の無確認削除になります。

最小修正案

v2 §10に1行追加 — 「--force（provider側の既存値の削除・上書きを伴う操作）は actor: agent の自動実行対象から除外し、Human confirmationを要求する。」 next --json が actor: agent のdeployアクションを出すときは force: false を含意すること。

C6. scrub() のメッセージがSecret長を漏らす（§3.1「Secret値のlength」禁止に対する既存違反）

severity: Low / affected: §3.1

根拠

packages/core/deploy/handoff.ts:135-143

if (value.length < 8) {
  return "(output withheld: secret too short to redact safely)";
}

この文字列は cli/index.ts:694-696 で stderr に出力され、mcp/tools.ts:236-239 でMCP responseにも載ります。つまり 「このSecretは8文字未満である」という1ビットが、Agentのcontextに入ります。

v2 §3.1 は「Secret値のlength」をAgentへ渡してはいけないものとして明示的に列挙しているので、これは新設計が引き継いではいけない既存の境界違反です。実害は小さい（1ビット、かつ極端に短い鍵に限る）ものの、v2が自分で引いた線を実装が跨いでいる状態です。

最小修正案

短い場合と長い場合でメッセージを同一にする（例：どちらも "(output withheld)"、あるいは非ゼロ終了時は常に出力を withhold する）。差分は数行。v2 §15-1 のcanaryテストに「長さ情報を含む分岐メッセージが出ないこと」を追記。

C7. writeGeneratedFile の --force パスは symlink を追従する → §15-9 を既存ヘルパの流用では満たせない

severity: Medium / affected: §5.1, §15-8, §15-9

根拠

packages/core/scanner.ts:295-298

writeFileSync(options.absolutePath, options.content, {
  encoding: "utf8",
  flag: options.force ? "w" : "wx"
});

wx（O_EXCL）は既存パスで失敗するのでsymlinkに書き抜けませんが、force: true の "w" は symlink を追従します。 前回Reviewerの実装案は agent-init でこの規約をそのまま踏襲するとしており（参考doc §3.3 / §8-3）、その通りに作ると agent-init --force で .claude/skills/api-key-case/SKILL.md や CLAUDE.md の位置に置かれた symlink 経由でproject外へ書けます。

v2 §15-9 は「symlink / path traversal等でproject外instructionを書き換えない」を必須テストにしているので、要件は正しいが、流用予定の既存実装がそれを満たしていないという状態です。

最小修正案

v2 §5.1 に「agent-init の書き込みは scanner.ts:writeGeneratedFile をそのまま流用せず、書き込み前に lstat で symlink を拒否し、解決後の絶対パスがproject root配下であることを検証する」と明記する。§15-9 のテストは既存ヘルパにも適用する。

P3. npx / supply-chain

severity: Medium / affected: §13

コードから確認した事実：

- package.json に postinstall / preinstall は存在しない（scriptsは build / build:worker / scan / test / verify / prepack のみ）。prepack はinstall時に走りません。よって npx -y の即時RCE面はパッケージ自体からは生じません。
- files は dist 中心で、bin は dist/cli/index.js。ネイティブ依存は @napi-rs/keyring（prebuild配布）。
- パッケージ名 api-key-case はハイフン3語で、typosquat耐性は高くありません。

したがって「@latest がRCEを招く」は言い過ぎですが、agent-init が managed instruction に npx -y api-key-case@latest を焼き込むと、そのrepositoryを開いたAgentが恒久的に「毎回レジストリから最新版を取って実行する」ようになります。 これはv2が新規に作る面で、§13が「具体方式はSecurity Review後に確定」としている通り未決です。

最小修正案（Reviewerとしての推奨）

- managed block には major line pin（api-key-case@0） を書き、exact pinはしない。AC-5（陳腐化しない）とsupply-chain境界の両立点がここ。
- agent-init は解決した exact version を block内のコメントとして記録する（監査用、実行には使わない）。
- agent-init --check を CI 用 drift 検査として §15 の必須テストに追加する（現状 §15 に drift 検査項目が無い）。

Product decision

D1. stdin承認の廃止範囲

v2 §8「Agent-first high-risk approvalのstdin経路を廃止する」と §9「fail closed」は、セキュリティ的には正しい。ただし副作用として、GUIの無いサーバー上で人間が自分のSSHターミナルから deploy --env production を実行する正当なケースが handoff-only で詰みます。

v2 §9 は「Phase 6 v1必須条件にしない」「将来 attend を別設計として検討」としており、判断としては筋が通っています。Reviewerとして追加で確認したいのは1点だけ：「Agent-first flowからの承認」と「人間が自分で起動した deploy」を、製品が実行時に区別できるのか。 区別できないなら §8 は後者も巻き込みます（区別の根拠が stdin.isTTY なら、それはC3と同じ理由で信頼できません）。

推奨：区別しようとしない。 「production/github承認はHuman Planeのみ。Human Planeが使えなければ拒否＋手順提示」で一貫させ、SSHケースは §9 通り Phase 6 v1 のnon-goalとして明記する。中途半端な検出ロジックを作るのが最も危険です。

D2. agent-init の書き込み先ホスト数

v2 §5.2「host固有ファイルを必要以上に生成しない」と AC-5「2回目以降bootstrap不要」は緊張関係にあります。前回案は .claude/skills/ + CLAUDE.md + AGENTS.md + .cursor/rules/*.mdc の4箇所でした。

書き込むファイルはすべて Agentへのinjectionチャネル（悪意あるPRがmanaged blockを書き換えられる）であり、かつ無関係なrepositoryの汚染になります。

推奨：既存マーカーが実在するhostにのみ書く（.claude/ があればClaude Code、AGENTS.md があればCodex、.cursor/ があればCursor）。検出ゼロなら何も書かず、stdoutのprotocolだけで完結させる（AC-1は成立、AC-5は次回bootstrapへ劣化）。これは製品判断です。

O1. §3.2 の Destination Identity を「account / organization / project」として意味的に解決する要求

現状 checkCli() は wrangler whoami --json / vercel whoami / gh auth status を実行しながら stdout を捨てて status === 0 しか見ていません（cloudflare.ts:27-34, vercel.ts:26-33, github.ts:23-30）。ここから account/org/project を意味的に取り出すには、3社分のパーサ＋wrangler.toml/.vercel/project.json の解釈＋失敗モードが増えます。

より小さく同じ目的を達する案：意味的解決をやめ、destination fingerprint にする。

sha256( 実行cwdのrealpath
      | 該当config file の内容hash（wrangler.toml / .vercel/project.json / git remote URL）
      | provider認証envのkey集合とhash
      | resolveCli の絶対パス＋size＋mtime
      | secret名 | target | env )

これを「信頼済みdestination」として保存し、毎回比較する。初回・変化時・production・GitHubで確認、というv2の分岐はそのまま使えます。パーサ不要、3社共通、C1/C2/C4の修正がそのままfingerprintの構成要素になります。 人間へ見せる表示だけは別途必要ですが、それは「解決」ではなく「表示」の問題に縮小します。

O2. §17 Phase D の「Vercel development restriction」は §10 と重複

§10で fail closed または Human confirmation と決まっているので、Phase Dの独立項目ではなく §10 の実装として扱えば足ります。実装順序の項目を1つ減らせます。
