# Security Policy

## Scope

This document describes version 0.9.1 and its Agent-first changes.
[Verification](docs/VERIFICATION.md) records measured results by revision;
[RELEASING](docs/RELEASING.md) distinguishes implementation from acceptance
and publication. Older design documents are not alternate approval policies.

API Key Case is an experimental local safety tool. It is designed to reduce accidental disclosure while preparing API integrations for AI coding agents. It does not guarantee complete safety — it is a tool that reduces the probability of an incident, not one that eliminates it — and it does not guarantee detection or prevention of every secret leak.

The CLI is expected to:

- avoid reading the contents of `.env` and `.env.*` files, except example templates;
- keep the scanner core free of network requests; a separate post-result telemetry path may make a best-effort request only when its own privacy gates allow it;
- avoid emitting full or partial detected secret values;
- preserve generated files unless replacement is explicitly requested with `--force`;
- report only variable names, file locations, Git state, and redacted findings.

### Secret storage boundary (`save` / `check` / `list` / `remove` / `trust`)

- Human-owned terminal use keeps the existing path: interactive hidden-input prompt → local CLI process memory → the OS secret store (Keychain / Credential Manager / Linux OS keyring).
- Agent-first Secret input uses `save <NAME> --ask`. On supported Windows and macOS hosts its separate Human Plane path is: password-dialog keystroke → fixed-path, sanitized helper-process memory → the native OS secret store. The helper writes the credential directly and returns only `saved`, `cancelled`, or `unavailable`; the value is never returned to the CLI parent. On macOS the JXA helper calls Security.framework directly with the existing `api-key-case` service/account naming, rather than placing the value in a `security` command, argv, environment, file, or parent-facing IPC payload. No function in the Human Plane interface returns a secret value.
- The Human Plane helper is resolved and verified at an OS-fixed absolute path: Windows PowerShell on Windows and root-owned, not group/world-writable `/usr/bin/osascript` on macOS. It runs from the fixed system directory with ignored stdio and a fresh environment: empty on macOS, and on Windows an explicit allowlist of `SystemRoot`, `WINDIR`, `SYSTEMDRIVE`, `PATH`, `PATHEXT`, `ComSpec`, `TEMP`, `TMP`, `USERPROFILE`, `HOMEDRIVE` and `HOMEPATH`. It does not inherit Agent-controlled `PATH`, `HOME`, `NODE_OPTIONS`, `LD_PRELOAD`, `DYLD_*`, provider authentication variables, or the project working directory. The Windows list is longer than it looks because it has to be: Node fills `PATH`, `TEMP`, `USERPROFILE`, `HOMEDRIVE`, `HOMEPATH` and `SYSTEMDRIVE` in from the parent process whenever the spawn omits them, so each one is *set* to a fixed system location, to a per-call scratch directory, or to the profile resolved through the OS rather than left out. `USERNAME`, `USERDOMAIN` and `LOGONSERVER` are still supplied that way; they name the caller rather than resolving code or files, and the helper reads none of them. If that boundary is unavailable, `--ask` fails closed and prints a handoff command for a human-owned terminal; it never falls back to the parent process's prompt.
- `check`/`hasSecret` uses the OS secret store's read API only to determine whether an entry exists, then immediately reduces the result to a boolean. It does not return, persist, log, or expose the value. This is distinct from the deploy handoff, which is the only path that must retain a value long enough to pass it to an official CLI.
- `save` never accepts a value as a command-line argument or piped stdin. The legacy prompt requires a human-owned TTY; `--ask` does not read stdin at all.
- `check` and `list` report only registered/missing status, names, scopes, and timestamps. The on-disk metadata index (`~/.api-key-case/index.json`) never contains a value, a hash of a value, or a value's length.
- Secret registration has two separate stages: the OS secret-store write and the value-free metadata/index update. If the store write succeeds but the index update fails, the CLI reports those facts separately and directs the user to `check <NAME>`; absence from `list` or `next` is not treated as proof that the stored Secret is missing.
- `history --json` reads advisory local deployment receipts (last 200 attempts per project) from `~/.api-key-case/deployment-history/`. Only names/scopes, destination-only identifiers, target/environment, force flag, random operation IDs, registration/operation timestamps and closed outcomes are persisted. The history module receives no value or provider output. Matching timestamps/destination selection never establishes value identity; current remote state is always uninspected. Editable, missing, stale or interrupted history supplies no approval, trust, entitlement, skip/retry or redeployment authority. Start persistence must succeed before handoff; result-save failure retains an unknown start and warns without retrying the write. Explicit deletion of the history directory removes only metadata. See the [history contract](docs/design/deployment-history.md).
- `remove` deletes a stored value only after a decision taken in that same Agent-independent Human Plane. There is no `--yes`, no stdin confirmation, and no fallback to the calling terminal: an agent that owns this process's stdin/PTY cannot complete a deletion, and when the Human Plane is unavailable the command fails closed and prints where a human can delete the entry themselves. A name that is registered nowhere is an error rather than a dialog, and a leftover metadata row whose stored value is already gone is cleared as index hygiene, not as Secret deletion.
- `trust status` reports which confirmed deploy destinations exist for this project; `trust forget` deletes those records after the same Human Plane decision. Forgetting is fail-safe in direction — it can only cause the next deploy to ask for approval again, never grant one — but it is still a security-state change, so an agent able to do it at will could raise approval dialogs until a human clicks through one. Neither subcommand can create or alter a trust record, neither reveals a destination fingerprint, and `trust forget` answers from the closed automatic-safe allowlist without touching a provider CLI for any target/environment that could never hold a record.
- Two consequences of `trust forget` worth stating rather than hiding. Forgetting a destination that has *changed* since your last approval clears the project/target/environment slot, so the next deploy's dialog says "first use of this destination" instead of "CHANGED since the last time you approved" — the approval is still required and still shows the full destination, but that one comparative warning is gone. And because the exact confirmation record is keyed by destination identity, forgetting while the destination cannot be resolved leaves that record in place; the command says so and exits non-zero rather than reporting a clean removal.
- The cleanup candidates in `next --json` come from the local metadata index (`~/.api-key-case/index.json`), which is an ordinary file an agent can write. That only ever supplies candidate *names*: the OS secret store decides whether an entry exists, a name that fails the closed validation is dropped, a name the project still references is never a candidate, and the human sees the real name in the dialog before anything is deleted. The worst an edited index achieves is proposing a deletion a human then refuses.
- The `Vault` interface deliberately has no method that returns a secret value; this is enforced by source review and by tests that grep for forbidden helper names.

### Deploy boundary (`deploy` / `targets`)

- A secret value's only path during `deploy` is: the OS secret store → `packages/core/deploy/handoff.ts` reads it once → it is written to the target CLI's (`wrangler` / `vercel` / `gh`) stdin → the in-memory reference is discarded. It is never placed in argv, an environment variable, a temporary file, or a log line. `handoff.ts` is the only module in this codebase allowed to retain the value for deployment; `vault/keyring.ts` may call the OS read API only for the boolean existence check described above. A test enumerates every deploy-related source file and confines value-bearing reads to those two modules.
- Captured child-process stdout/stderr is scrubbed for the value before it is shown, in case the target CLI ever echoes it back. Output withholding uses the same message for every Secret length; no length-dependent status is exposed.
- Every deploy that actually runs uses a single absolute CLI path captured before approval and re-stats it immediately before every child spawn. Windows resolves it from the Machine/User registry PATH. macOS ignores caller `PATH` and shell profiles and searches only a closed, architecture-aware set of system/Homebrew/MacPorts and OS-home-derived package-manager locations; repository-contained directories and CLI realpaths are rejected. The selected file's realpath, metadata, inode/device, and content hash are frozen. For a macOS Node shebang CLI, the already-running trusted Node executable is frozen the same way and the child is launched as exact interpreter realpath + exact CLI realpath; unknown script interpreters fail closed. The provider child receives the same closed PATH in a fresh environment. Only `--dry-run`, which executes nothing, still uses plain PATH inspection. Linux has no executing-deploy path in this release and fails closed with the provider's manual steps.
- On macOS the trusted home comes from the OS user database (`os.userInfo()`), not caller `HOME`. Provider children receive a fresh allowlist containing only the trusted `HOME`, frozen `PATH`, fixed `TMPDIR`, and fixed Git non-interactive/config isolation values; `NODE_OPTIONS`, `DYLD_*`, provider credentials, Git redirection values, and the rest of `process.env` are not inherited. The macOS Vercel Application Support auth locations and known Wrangler/GitHub locations are included in the existing auth-state snapshot.
- Deploying to `production`, every deploy to `github`, Vercel `development` (which is provider-readable), every `--force` operation, every `--scope user` deploy, and provider operations that can overwrite an existing value require the Agent-independent Human Plane. The fixed Windows PowerShell or macOS AppKit dialog displays the one operation and returns only an in-process status; it never reads the caller's stdin or creates a reusable approval token. On Windows 11 build 22000+, the WinForms affirmative button only starts the HWND-bound `IUserConsentVerifierInterop::RequestVerificationForWindowAsync` flow. Only `UserConsentVerificationResult.Verified` maps to approval; `DeviceNotPresent`, `NotConfiguredForUser`, `DisabledByPolicy`, `DeviceBusy`, `RetriesExhausted`, `Canceled`, unknown results, interop errors, and older builds all fail closed. Unsupported/unavailable Human Plane conditions fail closed.
- Any deploy must have one concrete destination before it proceeds: exactly one Wrangler config with `name` plus `account_id`, a linked Vercel project file with both org and project IDs, or a GitHub repository-root config with one `origin` remote on `github.com` and no include/rewrite ambiguity. The provider account identity is obtained from the same fixed CLI and sanitized environment, displayed without credential material, and queried again before every spawn. A different account aborts even if both states report “logged in.”
- Phase 6C extends the Windows/macOS Human Plane from Secret input to high-risk approval. After a successful Human Plane decision — including `Verified` on Windows — the same trusted call revalidates the fixed project realpath, destination config fingerprints, provider-auth environment presence, auth-file metadata, plan argv/pre-steps, and CLI file identity before reading the Secret and handing it to the same CLI. Config hashes use a closed projection of destination-only fields; Secret-bearing scalar values are replaced before hashing. Auth fingerprints contain file identity/timestamps only, not credential content, content hashes, or file sizes. A mismatch aborts without execution. The MCP path still refuses production/GitHub operations in two independent layers.
- Phase 6D adds the destination side of that boundary. A **Destination Identity** is a SHA-256 fingerprint of where a deploy would go: the fixed project realpath, the target, the environment, the destination-selecting repository config (path, kind, closed destination label, and the same Secret-free content projection used by the approval snapshot), and the non-credential provider account identity resolved through the fixed CLI and sanitized environment. It deliberately excludes the Secret name, scope, value, partial value, value-derived hash and length, provider credential values or hashes of them, auth-file timestamps, and the CLI file identity — the last two change on an ordinary token refresh or CLI upgrade and are re-verified inside the running call instead.
- Confirming an operation in the Human Plane records that identity, plus a `(project, target, environment)` slot used only to tell a first use apart from a changed destination. Both records live in the OS secret store as existence-only entries under a `v1|destination…` account whose value is a fixed marker, so no file write can mint one and they cannot collide with a Secret account. A trust record is not an approval token, a deploy permission, or access to any Secret: the engine still re-resolves the destination, re-applies the operation policy, and re-verifies the execution snapshot before every spawn. There is no CLI flag, MCP parameter, environment variable, or stdin path that creates or edits one. Anything able to call the OS credential API directly is already inside the OS-account trust boundary this tool relies on everywhere else.
- The automatic policy denies by default. `production`, `github` at any `--env`, Vercel `development`, `--force`, `--scope user`, any overwrite-capable or destructive step, an unconfirmed or changed destination, an ambiguous destination, a provider credential present in the environment, and anything outside the closed allowlist all require the Human Plane. The allowlist currently holds exactly one entry — Vercel `preview` in `project` scope without `--force` — because that call fails rather than overwriting and because the value cannot be read back afterwards. That second premise is this tool's own, not an inherited default: on Vercel, sensitivity is a per-variable setting independent of the environment (`--no-sensitive` exists, and the CLI's default has changed over time), so the adapter always plans `vercel env add … --sensitive` for `preview` and `production`. `preview` also plans `--yes`: the CLI asks which Git branch a Preview variable applies to, and a non-interactive child cannot answer, in which case `vercel` exits 0 without creating the variable (measured on 59.11.7, 2026-09-08). A test asserts that every environment on the automatic-safe allowlist still plans sensitive storage, so removing the flag cannot silently widen automatic execution. `development` never receives the flag, so its value stays readable back, which is why it is off the allowlist. Older Vercel releases also rejected the flag there; 59.11.7 accepts it, so this is now a deliberate choice by this tool rather than a provider restriction, and relaxing it would be a reviewed change to the allowlist premise rather than a flag edit. Cloudflare is excluded because `wrangler secret put` always overwrites.
- The deploy target is a closed list (`cloudflare` | `vercel` | `github`) fixed in source; it cannot be extended or redirected by a config file or environment variable.

### MCP boundary (`mcp`)

- `api-key-case mcp` exposes exactly 7 tools, a subset of the tools above: `list_required_secrets`, `check_secret`, `save_secret`, `deploy_secret`, `generate_env_example`, `scan_secret_leaks`, `check_gitignore`. None of their input schemas has a `value`, `secret`, or `password` property, checked by a test that inspects the actual registered schema, not just source review.
- `save_secret` never calls the vault. It returns a fixed `api-key-case save --ask` Human Plane action and still has no Secret value elicitation path.
- `deploy_secret` never completes a `production` deploy, or any `github` deploy (CI-reachable regardless of `--env`); it returns a fixed instruction asking a human to run `api-key-case deploy` instead. It never receives an approval parameter/token or uses MCP elicitation. Other high-risk plans fail closed because the MCP process has no Human Plane.
- Every tool response is built only from the same status objects the CLI renders. An unexpected exception inside a handler is converted to a fixed `NG:` message; the original exception message and stack are never forwarded.
- Transport is stdio only; there is no network listener, port, or multi-client session.

### License boundary (`license`, and the `deploy` gate)

- `license activate` is the only license operation that uses the network. It accepts a Lemon Squeezy purchase key only from hidden interactive TTY input; argv, piped stdin, and environment-configured destination URLs are rejected. The key is sent over HTTPS only to the exchange URL fixed in the published CLI.
- The exchange Worker validates the Lemon License API response, exact store/product/variant IDs, expiry/status, and the authenticated order's paid/refund/test-mode state before signing. It SHA-256 hashes the purchase key before using it as a 5/minute rate-limit key and separately limits `CF-Connecting-IP` to 30/minute; a missing IP shares a conservative fallback bucket. Neither the purchase key nor its digest is logged or returned. Rate Limiter errors fail closed before Lemon validation or AKC1 signing.
- Test and live use different Worker names, secret sets, and rate-limit namespaces. `LEMON_TEST_MODE` is fixed to `true` in the test Wrangler file and `false` in the live file; only the live Worker URL may be compiled into the CLI.
- The returned `AKC1` is verified locally before replacing any existing license file. Its signed payload shape and `id` field are unchanged; verified application state exposes that value as `entitlementId`, not an order ID. After activation, every Pro check is a fully offline Ed25519 signature check against the public key embedded in source; there is no license revalidation, machine binding, or expiry check. This does not disable the separate, privacy-limited usage telemetry path.
- The license key (`~/.api-key-case/license.key`) is stored in plaintext, unlike vault secrets — this is a deliberate, documented exception to the Vault boundary above, not an oversight. A leaked license key only lets someone else use the paid `deploy` feature; it never grants access to a stored API key, and its payload never contains personal information (no email, no name). See `docs/design/phase-5-license.md` §4.2 for the full rationale.
- The private signing key never lives in this repository, the published npm package, or test fixtures. It is configured only as the Worker's `AKC_ED25519_PRIVATE_KEY` secret. The legacy `tools/issue-license.mjs` remains excluded from npm as an emergency/manual recovery tool and refuses repository-local key material.
- Refunds and disabled licenses prevent future exchanges. An `AKC1` already issued for offline use cannot be remotely revoked; this is an explicit consequence of the good-faith, offline gate.
- An invalid, missing, or corrupted license file only ever blocks `deploy` / `deploy_secret`. It has no effect on `scan`, `save`, `check`, `list`, `remove`, or any other MCP tool.
- The v0.9.1 source remains public and inspectable under the Elastic License 2.0 (`Elastic-2.0`). The Pro purchase entitlement and offline license-key implementation are a separate layer; publishing the source does not remove the Pro requirement, and ELv2's standard limitations apply. The runtime boundary itself is unchanged — see the ADR in `docs/design/phase-5-license.md` §2.

### Telemetry boundary (`telemetry`)

- The scanner core remains fully local. Telemetry is called only after a targeted command has already determined its result, through a separate best-effort path that receives only the closed command/outcome contract — never the scan report, vault name, secret value, path, argv, or error text.
- The only initial event is `cli_command_result` for `scan`, `save`, `license_activate`, and `deploy`. Its allowed properties are the fixed `product: api_key_case`, fixed `surface: cli`, closed enums, or the product's own CLI version: `command`, `outcome`, optional closed `error_category`, `cli_version`, `os_family`, and `target` only for `deploy`.
- The event transport uses a product-configured, allowlisted PostHog capture host. It does not accept a destination URL from argv, project files, or a repository. The v0.9.1 distribution build includes the public PostHog Project Token used for event ingestion; it is not a Personal API Key or Project Secret API Key. `API_KEY_CASE_POSTHOG_PROJECT_TOKEN` is retained only as a non-empty development/test/override hook. Neither Personal API Keys nor Project Secret API Keys may be committed, bundled, or used for event capture.
- Telemetry is best-effort with a short timeout. A missing configuration, network/DNS failure, PostHog error, or timeout is swallowed and cannot alter stdout, JSON output, exit status, or the underlying command result. No telemetry is sent for MCP or the non-targeted status commands in the initial release.
- The anonymous installation ID is generated from cryptographically random bytes and stored only in the telemetry file, separate from the vault index and license file. It is never derived from hostname, MAC address, OS account, repository, license, email, or hardware. Disabling telemetry deletes it; re-enabling creates a new one.
- The default is enabled, but the first eligible target command with interactive stdin prints a one-time notice to stderr before any event. A run without interactive stdin sends nothing while that notice has not yet been shown; after a human has seen it, later non-interactive runs may send an event unless another suppression applies. CI and `DO_NOT_TRACK=1` always suppress telemetry, regardless of the persistent setting. `telemetry status` reports effective state without exposing the installation ID.

## Known limitations

The Free `next` schema-2 readiness report is advisory. It uses trusted deploy
resolution and sanitized provider identity probes without acquiring a Secret,
creating trust, requesting approval or deploying. It returns only closed status
codes and counts of Secret names. It does not establish Windows Hello enrollment,
a usable GUI session, remote Secret state or provider write permission. Pro
entitlement and every execution/approval boundary are still checked by deploy.
Generated Agent instructions guide conversation and sequencing; they do not
enforce approval or provide a guarantee that a third-party Agent follows them.

On Linux, the current native keyring dependency can fall back from Secret
Service to kernel keyutils. A successful availability probe therefore does not
identify the backend or prove persistence across login/reboot. The isolated
Linux verification lane separately checks Secret Service item paths without
reading their values; it does not extend Human Plane or deploy support to Linux.

Normal Agent-first support targets Windows 11 with Windows Hello. macOS is a
collaborative verification edition: current CI and real Keychain evidence are
available, while native GUI approval, Accessibility resistance, Intel hardware
and real-Mac provider deployment remain unverified. macOS verification continues
for a later promotion to regular support; it does not block the Windows-first
release. Do not purchase Pro relying on macOS deploy.

- **The Phase 6 Human Plane and executing deploy are implemented on Windows and macOS, but their release status differs by OS.** `save --ask` keeps the existing verified system PowerShell path on Windows. Windows high-risk approval, `remove`, and `trust forget` additionally require Windows 11 build 22000+, Windows Hello (PIN, fingerprint, or face) set up for that account, and an OS verification result of `Verified`. Windows 10, an account with no Hello configured (`NotConfiguredForUser`), no verifier device (`DeviceNotPresent`), and a policy that disables it (`DisabledByPolicy`) all return `unavailable` for those decisions — the same handoff-only position as Linux — without disabling scan, vault, or Secret input. Because `deploy` is the paid feature, check that requirement before purchase. macOS continues to use `/usr/bin/osascript` with AppKit/Security.framework and remains a collaborative verification edition pending native acceptance. A headless/blocked GUI session or failed helper/verification path returns `unavailable` and hands off; it never uses an Agent-owned TTY. Executing deploy additionally requires a safely discovered provider CLI in the platform's closed trusted locations. Linux remains handoff-only for these operations, while `--dry-run` still works everywhere as a Pro plan-only check. Intel candidate paths are implemented but have not yet been verified on Intel hardware.
- **Windows user verification is not documented here as a Secure Desktop guarantee.** It is an OS-mediated identity check associated with the plan window, and it repairs the measured UIA/MSAA path in which a sibling process actuated the product's own button. It does not make a compromised Windows account trustworthy, prove that every verifier configuration uses Secure Desktop, or defend against an attacker that can steal the user's verifier secret, run elevated/debugger-level process tampering, or compromise Windows itself. The verifier confirms the current user, while the visible plan, one-shot call, and post-verification snapshot checks continue to bind that decision to the operation.
- **macOS approval does not have the Windows OS identity check.** The current AppKit helper maps the affirmative dialog result directly to approval for deploy, Secret removal, and destination-trust removal. Its fixed executable, sanitized environment, and default No button do not establish that a human actuated that button. Whether a same-user process with Accessibility permission can approve through the product's dialog remains unmeasured; this includes a terminal or IDE to which the developer has granted that permission. TCC is not treated as proven protection here. The implementation is retained pending native measurement and human review, not because equivalent protection has been established. Portable script tests and green CI cannot settle this gap, and this disclosure does not establish regular macOS support. The current macOS edition remains collaborative verification pending separate acceptance. See the [macOS verification plan](docs/design/macos-human-plane-verification.md) and [release checklist](docs/RELEASING.md#current-os-support-status--2026-09-13).
- **A destination trust record does not expire.** Phase 6E adds `trust status` and a Human-Plane-gated `trust forget`, so a record can be inspected and removed — but nothing removes one on its own. A destination that changes simply stops matching and asks again, and a destination that changes back to a previously confirmed state is trusted again because it is the same destination. `trust forget` needs the current destination to resolve in order to delete the exact confirmation record; when it cannot resolve (no CLI installed, not logged in), it still clears the project/target/environment slot, reports that the confirmation record may remain, and exits non-zero.
- **Once handed off, it's out of this tool's hands.** `deploy` writes a value to `wrangler`, `vercel`, or `gh` on their stdin and discards its own reference — but the value now lives inside that official CLI's own process, subject to its logging and behavior. Output scrubbing (Deploy boundary, above) covers what comes back to this CLI, not what the target CLI does internally. In particular, a value deployed to Vercel's `development` environment is readable again afterwards: this tool does not pass `--sensitive` there, so `vercel env pull` can write it back out to a local `.env` file. (Older Vercel releases rejected the flag in `development`; 59.11.7 accepts it, so this is this tool's own default now — see the automatic-policy note above.) `production` and `preview` are created with an explicit `--sensitive`, so those are not readable back — but a `vercel` CLI too old to accept the flag fails the deploy rather than falling back to a readable variable, and this tool cannot undo a variable a person later re-creates without it. Cloudflare Worker secrets and GitHub secrets — repository or environment — are not readable back.
- **A person can always paste a secret by hand.** Nothing here stops someone from reading a value out of the OS secret store's own UI and typing or pasting it into a chat window, ticket, or AI conversation themselves. The Vault, deploy, and MCP boundaries only close paths this code itself controls.
- **The OS secret store is only as strong as the OS account.** This CLI relies on the platform's own access control (macOS Keychain, Windows Credential Manager, or the Linux OS keyring) rather than adding a second layer of its own; anything that can already authenticate as your OS user is operating inside the same trust boundary as this CLI.
- **This tool assumes the integrity of its own installed code and running process.** It is an npm package: anything running as your OS user can rewrite the installed files under `node_modules`, attach a debugger to the CLI process, or call the OS credential API itself. Such a process can therefore make the CLI behave however it likes — including skipping a Human Plane decision — but it never needed the CLI in the first place, because the same access reads the stored value directly. The boundaries above are about what an agent can achieve *through this tool* using its ordinary, documented, unprivileged capabilities: your terminal, its stdin, argv, environment variables, files it can write, accessibility APIs it can call, and exit codes it can observe. The measured Windows case that Human Plane verification repairs — a same-session sibling driving the product's own button through MSAA — is exactly that class. Tampering with this tool's own code or memory is not, and is treated as an already-compromised OS account.
- **Scanning is heuristic, not exhaustive.** `scan` matches a closed set of known token shapes, only reads specific text file extensions, skips `node_modules`/`dist`/build/vendor directories, and ignores files over 1 MB. An unfamiliar key format, a binary asset, or a skipped path will not be flagged. Treat a clean scan as "nothing obvious found," not "nothing there."
- **A Pro license, once exchanged, is offline and cannot be pulled back.** A refund or disabled license blocks the *next* exchange; it does not revoke an `AKC1` a machine already holds (License boundary, above).
- **Detecting a leak does not undo it.** See "If a credential was exposed" below — rotation at the provider is the only thing that actually closes an exposure.

## Reporting a vulnerability

Do not include a real credential, `.env` file, access token, private key, or unredacted scan output in a report.

Use [GitHub Private Vulnerability Reporting](https://github.com/melavern/api-key-case/security/advisories/new). If that route is unavailable, email [dev@melavern.com](mailto:dev@melavern.com). Do not include credentials or other sensitive values in the email; use fake canaries and redact output. For non-security questions, follow [SUPPORT.md](SUPPORT.md).

Include:

- the affected version;
- operating system and Node.js version;
- minimal reproduction steps using fake canary values;
- the output after manually removing any sensitive material;
- whether you have evidence that the issue is already being exploited, or
  that a real credential was exposed through it. Say so in the first message:
  it decides how fast the maintainer has to act and whom to notify.

## If a credential was exposed

`scan` finding a leak — or you noticing one yourself — does not undo it. The credential is compromised from the moment it left your control, not from the moment someone spots it in a diff.

1. **Rotate it at the provider first, before anything else.** Generate a new key/token and revoke the old one from the provider's dashboard or API. Every minute the old value stays valid is a minute someone else can use it.
2. **Update everywhere the old value was actually used**: `api-key-case save <NAME> --force` to overwrite the local vault entry (or `api-key-case remove <NAME>` if the key is being retired rather than replaced), then re-`deploy` the new value to any Cloudflare/Vercel/GitHub target that had the old one.
3. **Review the provider's audit or usage logs** for the exposure window to check whether the old key was used by anyone else.
4. **Clean up the exposure as a follow-up, not a substitute for step 1**: remove the value from the working tree, and if it reached Git history, rewrite history (for example with `git filter-repo` or BFG) and force-push, keeping in mind that any existing clone or fork already has it.

Deleting a local file or rewriting Git history does not invalidate a leaked credential — only revoking it at the provider does.

## Supported versions

Before the first stable release, security fixes are provided only for the latest published version.
